# Architect Assistant

A Dynatrace AppEngine app that helps an architect confirm which onboarding best practices are **in place vs missing** in a tenant, with a coverage score per check and drill-down to the entities that are missing them.

**Detailed documentation:** [docs/](docs/README.md) has one page per tab: every section, check, DQL query (in full, explained line by line), API call and remediation action. Each tab links to its page in its top-right corner (`TAB_DOCS` in `ui/app/areas.tsx`).

## What it checks (v1)

An **area** dropdown above the tabs picks which tabs are shown; each area has its own glyph and colour (the colour edges the bar the dropdown sits on), and remembers the tab you last opened in it. Links that jump to another tab (Top findings, the (i) buttons, the Frontends gauge) switch the area too.

| Area | Tabs |
| --- | --- |
| Metadata (label glyph, blue) | Entity Overview, Data Overview, Host groups, Security context, Cost allocation, Ownership & Teams, Primary tags |
| Migration Assistance (upgrade glyph, orange) | SLOs, Segments, Problem notifications |
| Visibility (eye glyph, aqua) | OneAgents, Deep Monitoring, Frontends, ActiveGates, Network Zones, Kubernetes, Databases, Extensions, Service Detection v2 |
| Users and permissions (key glyph, violet) | IAM Policy Creator, IAM Boundary Creator, Permissions Test |

## Remediation actions

Every tab except Overview ends with a **Remediation actions** section: an *Action* dropdown (API or Manual) plus a short form. Writes always offer a validate step and an explicit confirmation, and show the exact request.

| --- | --- | --- |

| Enable automatic OneAgent updates (OneAgents) | 1 GET + 1 PUT/POST | `builtin:deployment.oneagent.updates`, environment scope |

## Databases tab: matching and remediation

Nothing in Smartscape links a DB instance to a host or process (its only edges are `DB_DATABASE runs_on` and `SERVICE calls`), so the queries match them by name and address, per technology (MariaDB and MySQL count as one for matching):

- **Server name**: the DB instance's `host.name` (the name the database reports, for example SQL Server's `@@SERVERNAME`; SAP HANA's host) equals the process's pod, host (or its first label), workload or container name. No port is needed: endpoints often go through a load balancer (the SQL Server instance `MSSQLSERVER@easytrade-db-0` on the demo tenant is reached through an ELB and matches the `easytrade-db-0` pod this way).
- **Endpoint**: the connection host (or its first one or two labels, never taken from an IP address) or IP equals the process's pod, workload, `workload.namespace`, host name or a host IP, and the endpoint port is one the process listens on (any port when OneAgent reports none).
- **Local extensions** (Redis, MongoDB local, SQL Server local) create no DB instance; a process counts as covered when such an extension reports `dt.sfm.extension.status` from its host.

Database servers are found by `processType` (SQL Server, MySQL, PostgreSQL, MongoDB, Redis) or by the server executable (Oracle `oracle`, Db2 `db2sysc`, SAP HANA `hdbnameserver`, `mariadbd`, `valkey-server`); MariaDB in images that keep the `mysqld` name is recognised by its executable path. The summary query computes every pair once with an outer join, so its counts equal the two tables (checked for 24 hours, 7 and 30 days on the demo tenant).

*Configure* (or *Details*) on a database process runs these checks, with three API reads (the extension in the environment, its monitoring configurations with their statuses, extension credentials in the credential vault):

| Check | Source | Fix offered |
| --- | --- | --- |
| Covered by an extension | the matching DB instance (and what it matched on) or the local extension on the host | — |
| Extension in the environment | Extensions API: active version, installed but not active, or not installed | Manual: add it from Dynatrace Hub (link) / activate a version in the Extensions app |
| ActiveGate group with the Extensions module (remote extensions) | Smartscape `ACTIVEGATE` with `EXTENSION_CONTROLLER`, online in the last 20 minutes, by group | Manual: put an ActiveGate with the Extensions module in a group that reaches the database (`agctl group set`, `[collector] group`, `--set-group`), restart |

| A configuration already targets this database | the extension's monitoring configurations whose endpoint is the process's pod, workload, service DNS name, host or IP (and port), with their status | Manual: fix that configuration (endpoint, credentials, ActiveGate reach) instead of adding another |

## Extensions tab: sources, broken configurations and recommendations

Where a configuration runs and what it is assigned to exist only in the Extensions API: one list call, then one `monitoring-configurations` GET per extension (six at a time). `scope` is `environment`, `HOST-…`, `HOST_GROUP-…`, `ag_group-<name>`, `kubernetes` or `integration-<cloud>`; `activationContext` is LOCAL, REMOTE, CONTAINER or DATA_ACQUISITION (older extension versions have none, then the scope decides). The status comes from extension self-monitoring, reusing the ActiveGates tab's query for remote configurations plus one for the rest (local configurations report one series per host; Kubernetes ones carry neither host nor group; cloud data acquisition reports none and is shown as *not reported*, never broken). A configuration without any status series takes the status of its latest framework error (for example *not picked up for execution*), otherwise *NO_DATA*. Without the Extensions API (403) the tab falls back to DQL only and says so.

**Fastcheck** results are the extension framework's assignment events (`dt.system.events`, `EXTENSION_FRAMEWORK_CORE`): *Failed to assign monitoring configuration to ActiveGate. Reason: Fast check failed …* (or the authentication / connection error the check returned), *Successfully assigned …*, *… has not been picked up for execution*. A failing check repeats about hourly, so the log folds repeats into one row with a count and the first and last time.

*Fix* on a configuration runs these checks: the status (and where it came from), the scope (host or host group seen in the last 30 days and reporting the configuration; environment), the hosts that are not OK, the ActiveGate group (an ActiveGate with the Extensions module, connected), the latest fastcheck result and the latest framework error. Actions (manual, doc-backed): *Fastcheck failed* (what the check is, the usual causes, the DQL for the results), the ActiveGates tab's *Extension not running* steps for remote configurations, and *Local configuration not running* (scope inheritance environment → host group → host, re-scope configurations whose host is gone).

**Recommendations.** Network devices run no OneAgent, so SNMP is judged from the installed SNMP extensions and their enabled configurations: SNMP Autodiscovery (scans subnets and IP ranges for SNMP-enabled devices, lists them as entities and points each one to the extension that fits; needs an ActiveGate 1.280+ with the API routing module and a platform token with `storage:buckets:read` and `storage:smartscape:read`) and the device extensions (Generic network device, Cisco, Juniper, F5 BIG-IP, Palo Alto and any other SNMP extension). Process technologies are matched on `processType`, the software technology type, the executable, the Java main class or jar (RabbitMQ only on Erlang broker processes and Kafka only by the broker's main class: OneAgent reports both on client applications too); extension IDs and names were checked against the Dynatrace Hub catalog. A host is covered when a matching extension reports a status from it. The recommendation query uses an `id in [subquery]` prefilter: 2.6 s for 30 days on the demo tenant instead of 10.8 s.

## Service Detection v2 tab

SDv2 detects and names services from resource attributes with one rule set for OneAgent and OpenTelemetry, and makes one service per process. Per the docs (fetched 2026-10-24), it is generally available for Kubernetes (SaaS 1.323+) and AWS Lambda (1.337+) services monitored by OneAgent. For generic workloads outside them it is Early Access (1.343+). OpenTelemetry services always use SDv2. Switching gives the matching services new IDs and metric keys.

**Data.** One DQL query (`sdv2ServicesQuery`). Smartscape `SERVICE` nodes carry `dt.service_detection.version` and, for SDv1, `dt.service.sdv1_type`. Their edges give the Kubernetes namespace, cluster and workload, the processes (host group, process group) and AWS Lambda functions they run on, and the frontends and HTTP monitors that reference them. Classic `dt.entity.service` adds the technology, the web application / context root and the software technologies. The settings come from one paged GET (all scopes) over `builtin:service-detection-v2-for-oneagent`, `builtin:service-detection-rules`, `builtin:service-splitting-rules`, `builtin:endpoint-detection-rules`, `builtin:endpoint-detection-rules-opt-in` and `builtin:url-path-pattern-matching-rules`.

**Recommendation per SDv1 service** (`ui/app/sdv2.ts`, from the docs' *Which workloads to activate* section):

| Verdict | When |
| --- | --- |
| Enable (GA) | The service belongs to a Kubernetes namespace or runs on AWS Lambda. |
| Pilot (Early Access) | A process outside Kubernetes and Lambda with one application: web servers (NGINX, Apache, IIS) and single-service apps. |
| Review first | The same, but an SDv1 custom service: SDv2 ignores custom services, so their spans join the process's service. |
| Keep on SDv1 | WebSphere / WebLogic, several web applications or context roots in one process (multi-context JVMs), background activity without an inbound request, CICS / IMS, or no process, Kubernetes or Lambda context. |

Scope rows show the estimated number of SDv2 services after the switch: distinct workloads for Kubernetes, process groups for generic workloads. SDv2 merges the SDv1 services of one process into one service, so 14 SDv1 services can become about 12. A host group that has workloads to keep on SDv1 is marked *Pilot selected process groups* instead of the whole group.

**Built-in rule checks** come from the footnotes of the docs' default-rule tables:

- `[Built-in] OpenTelemetry service name` on, and its `(deprecated)` twin off.
- `[Built-in] Split services by k8s cluster and namespace` on, and the namespace-only split off.
- `[Built-in] Split services by host group and primary cloud fields` on. This is the default for new environments, and it is pre-selected when there are generic workloads.
- `[Built-in] FaaS name` on (SDv2 for Lambda needs it).
- `[Built-in] HTTP fallback for derived route (legacy naming)` off, so endpoints get derived names instead of `GET /*`.
- The endpoint detection opt-in on, when that object exists.

Rules are matched by name. A check whose rule is missing on the tenant is left out.

**Remediation actions.** Every API action shows its request and has a *Validate* step (the same request with `validateOnly=true`), followed by a confirmation and *Apply*. New objects go in one POST. Each existing object gets one PUT that keeps its other values.

- *Apply recommended built-in rules*: one PUT per selected rule; only `enabled` changes.
- *Enable SDv2 for Kubernetes workloads*: namespaces (staged rollout; *Recommended* selects every namespace with SDv1 services), clusters or the environment, with an optional matching condition.
- *Enable SDv2 for AWS Lambda (FaaS)*: the environment, with the schema's default condition `isNotNull(aws.region) and isNotNull(aws.account.id)`.
- *Pilot SDv2 for generic workloads (Early Access)*: you pick process groups per host group. A whole host group gets `dt.host_group.id == "<name>"` at the host-group scope. Otherwise the condition lists `dt.process_group.detected_name == "…"` (both forms are the docs' examples). Hosts without a host group use the environment object. An existing condition is kept and OR-ed with the new one, and the form checks the 1000-character limit.
- Manual actions: update dashboards, alerts and SLOs after the switch; replace `GET /*` endpoints with URL path patterns; name services at the source with `OTEL_SERVICE_NAME`; adjust SDv2 names with a detection rule.

Links open the Settings app on the schema (and scope) via `dynatrace.settings/open_settings_for_schema`, host groups in Infrastructure & Operations, and services in the Services app. The payloads follow the tenant's schemas (`dtctl get settings-schema`). They were exercised offline with mocked Settings responses, not written to the tenant, because the dtctl token has no Settings write scope. *Validate* is the live check.

## IAM Policy Creator and IAM Boundary Creator tabs

Two builders for the text you paste into Account Management (Identity & access management > Policy management). Each tab has the GUI on the left and the live text on the right; the text is a code editor that updates as you select, can be edited by hand, and is validated as you type (problems are underlined, marked in the gutter and listed under the editor with their line). Under the editor: **Copy to clipboard** and **Export .txt** (file named after the policy or boundary name), and links to the IAM docs pages. Every permission, service and global condition links to its section of the docs.

**Where the permissions come from.** Permissions change often, so nothing is hardcoded: the `iam-reference` app function ([api/iam-reference.function.ts](api/iam-reference.function.ts)) reads the [IAM policy reference](https://docs.dynatrace.com/docs/manage/identity-access-management/permission-management/manage-user-permissions-policies/advanced/iam-policystatements) and the [global conditions](https://docs.dynatrace.com/docs/manage/identity-access-management/permission-management/manage-user-permissions-policies/advanced/iam-global-conditions) page once per page load and parses every service, permission, condition and the operators each condition supports ([api/iam-reference-parser.ts](api/iam-reference-parser.ts); 43 services, 228 permissions, 8 global conditions on 2026-10-24). The banner at the top of both tabs says whether the live docs were read and lists what they changed since the bundled snapshot (`ui/app/iamSnapshot.json`, used until the live read arrives and whenever it fails, for example when docs.dynatrace.com is not in the allowed outbound connections). A permission typed in the editor that the docs don't list is flagged, not rejected.

**IAM Policy Creator** works in three steps (the step buttons show progress; the draft keeps the current step):

1. **Apps:** every installed app (App Registry) as a card with its icon; search, and filter All / Dynatrace / Custom / Selected. Clicking a card selects it (check mark and green border) with Read; the dropdown under each card offers Read, Write and Execute, but only the levels the app's manifest uses (Read for viewing actions: read, list, download; Write for changes: write, delete, admin, restore, share; Execute for actions: run, execute, use, send, invoke). Each option lists how many permissions it adds; Read warns when the app shows Grail data and names the tables, and Write warns when it includes writing data into Grail (Notebooks, for example). Each selected app gets its own `ALLOW app-engine:apps:run WHERE shared:app-id = "<app>";` line, then the permissions its manifest requests for the chosen levels, each on its own line with the apps that need it as a trailing comment. App state and app settings permissions (`state:*`, `app-settings:*`) are limited to the selected apps with `shared:app-id` (option). Manifest scopes that are not IAM policy permissions (`environment-api:*`, `iam:users:read`, …) and the app's own `app-engine:apps:run` (it lets the app open other apps) are left out and listed. *Customize* on a selected app unticks individual permissions. *Let the group open every app* writes one unconditional `app-engine:apps:run`.
2. **Data access:** the Grail table permissions the selected apps read (manifest scopes on storage tables with record-level conditions), each with the apps that need it; ones the manifest marks "(Optional)" and sensitive fieldsets start unticked. Nothing is added until *Add data access* is chosen; until then the policy text carries a `// ⚠ <app> shows Grail data this policy does not grant yet (…)` comment, the editor marks the app's line, and the app card and step button show a warning. `storage:buckets:read` is added for the included tables (limited to those tables, or by the Grail bucket dimension). Below, **dimensional data** (security context, bucket, host group, Kubernetes cluster and namespace, host, AWS / Azure / GCP accounts, frontend, event kind / type / provider, log source, metric key, entity type) limits the records; AND puts all dimensions in one statement, OR writes one statement per dimension. When a permission does not support the chosen operator, the equivalent one is written for it (MATCH without wildcards = IN or =, one `prefix*` = startsWith; on entities IN / startsWith already match any element of a multi-value security context) and the step says so; only operators with no equivalent are errors.
3. **Fine-tune:** any permission from the reference on top (search or browse all services), with ALLOW / DENY, any of its own conditions with any documented operator, global conditions, and *+ Statement* for another statement on the same permission (OR). **Global conditions** (environment, user, user domain, group, date, date-time, time of day, week day) are added to every statement.

Options: comments (section titles and the apps behind each line), and *Fewer statements*, which combines permissions with the same conditions (off by default: one ALLOW per line; turn it on if a policy nears 100 statements). *Start from a docs pattern* loads the policies shown in the Grail and Settings docs; *Load this text into the builder* turns hand-edited or pasted text back into selections (apps become *open only*, everything else step 3 permissions). Drafts saved by the first version are migrated.

**IAM Boundary Creator**

- **Apps** (one `shared:app-id` line), **dimensional data** (one line per service you tick: storage, settings, synthetic, dev-obs where the attribute exists), and **more conditions** (any condition key from the reference, including `environment:management-zone`, settings schema / scope, extensions, tables, fieldsets and global conditions). Each line says which permissions it narrows.
- **Check against a policy:** applies the boundary to the Policy Creator's policy (or any pasted policy or docs pattern) with the rules in [How are policy boundaries applied?](https://docs.dynatrace.com/docs/manage/identity-access-management/permission-management/manage-user-permissions-policies/iam-policy-boundaries#apply-boundary): statements are split per permission, only conditions the permission supports are added (global ones always), repeated conditions multiply a statement, and DENY stays as it is. Every effective statement is marked *narrowed*, *own conditions only* or *unrestricted*, so a permission the boundary does not narrow (the docs' `storage:entities:read` example) is visible before the boundary is used. The docs' own example reproduces exactly.

**Checks in the editor** (from the syntax, boundary, Grail permissions and limits pages): statements start with ALLOW or DENY and end with `;`; permissions have the form `service:resource:action`; a condition must be supported by every permission in its statement, with a supported operator; IN / NOT IN / MATCH take a parenthesised list, the others one quoted value; no OR (write another statement); straight quotes only; at most 100 statements per policy; boundaries hold at most 10 conditions, one per line, no AND / ALLOW / DENY / WHERE. Warnings and notes: conditional DENY on Grail table permissions runs as an unconditional DENY, unconditional DENY, table permissions without `storage:buckets:read`, `storage:query-consumption` values other than INCLUDED / ON_DEMAND, date and time values without a time zone, week-day names, `${bindParam:…}` binding parameters (bound through the Account Management API only), MATCH wildcards away from word separators, repeated boundary conditions.

**Value pickers.** Every value field accepts typed values, `${bindParam:<name>}` binding parameters and the global attributes `${global:userId}` / `${global:userGroup}`, and suggests values from the tenant once opened: field values seen on Smartscape nodes, logs and spans (sampled) and metrics (at most 10 days, the `metrics` command's limit) for the record-level fields; buckets and tables from `dt.system.buckets`; event fields from events, business events and system events (5 GB scan cap); log sources, metric keys, entity types, process groups, hosts, host groups and ActiveGate groups from DQL; apps, settings schemas (and a schema's groups on request), management zones and extensions from their APIs. Sections backed by DQL show the DQL actions. Formats the reference does not document (`settings:entity.hostGroup`, `extensions:host`, `extensions:host-group`) are marked as such; their suggestions are entity IDs.

**Drafts** live above the tabs and in this browser's localStorage, so switching tabs or reloading keeps them; *Clear all* starts over. AI Assist reads the editor text (hand edits included): selected apps that show Grail data the policy does not grant, data access without any dimensional data, statement count against the limit, unconditional table permissions, missing bucket access, DENY pitfalls, MATCH for list-valued security context, and, for boundaries, the permissions the preview shows as not narrowed.

## Permissions Test tab

Answers "what can this user (or group) actually do here?" for the current environment.

**Who to test.** *User* finds users whose email contains the text or whose name starts with it; *Group* finds groups whose name contains it (3 characters or more). The search uses the environment's IAM API (`@dynatrace-sdk/client-iam`, scopes `iam:users:read` / `iam:groups:read`); if that is not allowed for you, it falls back to the account's user and group lists. Clicking a result runs the test; a full email or a group UUID can also be tested directly. *Policy Creator draft* tests the IAM Policy Creator's policy (with the IAM Boundary Creator's boundary, optional) as if it were the only policy bound to a group, live as the drafts change, with no Account Management access.

**Where the data comes from.** Group membership, policy bindings, policies and boundaries are only exposed by the account-level [Account Management API](https://docs.dynatrace.com/docs/dynatrace-api/account-management-api) (`api.dynatrace.com`), so the `iam-access` app function ([api/iam-access.function.ts](api/iam-access.function.ts)) calls it with an OAuth client of the account: the user (and their groups), the bindings on the account and on this environment that name those groups (with boundaries and bind parameters), the bound policies wherever they are defined (`policies/aggregate`, so Dynatrace default policies are included) and the boundaries. Nothing is written.

**Setup** (the *Account Management access* card does steps 3–4 for you):

1. In Account Management > Identity & access management > OAuth clients, create a client with `account-idm-read`, `iam:bindings:read`, `iam:policies:read`, `iam:boundaries:read` (accounts without the fine-grained IAM scopes: `account-idm-read` + `iam-policies-management`; the function tries the read-only set first). Note the account UUID shown there.
2. Add `sso.dynatrace.com` and `api.dynatrace.com` to the allowed outbound connections (`builtin:dt-javascript-runtime.allowed-outbound-connections`) when that allowlist is enforced.
3. Save the client ID, secret and account UUID in the card. It is stored in the credential vault as the *User and password* credential `architect-assistant-account-api` (App Engine scope; account UUID in the description).
4. *Only I can use it* (default) makes the credential owner-only, so other users of the app cannot run the test. Turning it off lets everyone who can run the app read the account's groups, policies and boundaries through it.

**How access is worked out.** The policy text is evaluated with the IAM Policy / Boundary Creator engine (`ui/app/iamAccess.ts` on top of `iamPolicy.ts`): bind parameters are filled in (policies and boundaries), each boundary of a binding is applied with the documented rules (several boundaries on one binding are applied separately and add up), `${global:userId}` / `${global:userGroup}` are resolved for the subject, and every effective statement is checked against the request: DENY wins over ALLOW, and a conditional DENY on a Grail table permission runs as unconditional ([Permissions in Grail](https://docs.dynatrace.com/docs/platform/grail/organize-data/assign-permissions-in-grail)). Conditions on the environment, user and group are decided; date / time windows, unbound parameters (and user conditions when testing a group or a draft) make a result *conditional*; conditions on records or resources (security context, bucket, …) make it *limited*.

**Apps.** Every installed app (App Registry, with the same icons and manifest analysis as the Policy Creator), sorted with usable apps first, filterable by status and Dynatrace / custom:

- ✓ **Access:** `app-engine:apps:run` covers the app and the Grail data its manifest requires is readable (possibly limited by dimensional data).
- ⚠ **Conditional:** opening it depends on a date / time window, the user or an unbound parameter, or some of the data it requires cannot be read (the app opens but those views stay empty).
- ✗ **No access:** no ALLOW of `app-engine:apps:run` covers it, or a DENY does.

Other manifest permissions do not change the status (manifests request every scope an app may use); each card shows Read / Write / Execute coverage (green = all, amber = some, red = none), and clicking a card shows the statement that opens it (policy, group, boundary), the data it shows and every manifest permission with its result.

**Dimensional data.** One tile per Grail table permission (plus bucket access), then *By table*: what is readable (all records, limited, conditional, no access, denied), the conditions that limit the records (statements combine with OR, conditions within one with AND), the bucket access for that table (`storage:buckets:read` evaluated with the table name), and the policies behind it. *Records query* shows a DQL that counts the records the subject can read by the limiting dimensions (Show DQL, Copy, Open in Notebook, Add to Dashboard). It runs with your own permissions and uses case-insensitive `matchesValue`, so it is a preview. *By dimension* lists, per dimension, the values allowed and on which tables. **Where the access comes from** lists each binding (policy, level, group, boundaries, parameters) with its effective statements, and *Copy effective statements* copies them with their sources.

Classic environment roles (`environment:roles:*`) are listed in the effective statements but are not evaluated for app access, and settings permissions are not resolved per schema object.

## Keeping the guidance current (Deep Monitoring, Service Detection v2)

Supported versions, blockers and steps live in `ui/app/deepTech.ts` / `deepActions.ts` (Kubernetes tab: `ui/app/kubernetes.ts`; ActiveGates tab: `ui/app/activeGates.ts`; Service Detection v2 tab: `ui/app/sdv2.ts`), written from the Dynatrace docs. Every cited page is in `DOC` (deepTech.ts). They are not rewritten automatically (parsing docs pages into remediation logic would be unsafe), but doc changes are detected:

- **In the app:** the `docs-freshness` app function ([api/docs-freshness.function.ts](api/docs-freshness.function.ts)) reads the docs sitemap (one request; every page has a lastmod date) and the tab compares it with `ui/app/deepDocsSnapshot.json`, the dates recorded at the last review. The remediation header shows the review date and the result; a fix whose cited page changed or disappeared gets a notice and a marker on that link, and the diagnosis flags a changed technology support page above the supported-version check. Setup: when `builtin:dt-javascript-runtime.allowed-outbound-connections` is enforced (it is on the demo tenant), add `docs.dynatrace.com`; until then the header says the check is off. Vendor pages (nodejs.org, go.dev, …) have no sitemap date and are not tracked.
- **Watched sections:** SDv2 changes often, so its whole docs section (`DOC_SECTIONS` in deepTech.ts) is tracked too, and the function returns every sitemap page under that path. When a page there is updated or published after the review, the Service Detection v2 tab shows a banner and marks the affected fixes. The *Service Detection v2 documentation* card lists each page's reviewed and live date.
- **For maintainers:** `npm run check-docs` lists cited pages updated since the review, pages no longer in the sitemap, new citations and new pages in watched sections (exit code 1 if any, so it can run in CI or on a schedule). After reading them and updating the catalogue, `npm run check-docs -- --accept` records the new dates.
- **IAM tabs:** the permission catalogue is read live (see the IAM section above), so it needs no review. `npm run sync-iam` lists permissions, conditions, operators and global conditions that differ from the bundled snapshot (exit code 1 if any); `npm run sync-iam -- --write` refreshes `ui/app/iamSnapshot.json`. If the docs page layout changes so that it parses to almost nothing, the function reports an error and the tabs keep the snapshot; fix [api/iam-reference-parser.ts](api/iam-reference-parser.ts).

## Data sources

All data comes from DQL run in the browser against Smartscape (`smartscapeNodes`), chosen over scanning logs/events/metrics because it is cheap and carries the primary Grail fields on each entity. Every query uses an explicit `from:now()-<timeframe>`. Compliant and total counts are produced by one query (`coverageQuery`); drill-down queries only run when a user opens one. All queries are in [ui/app/queries.ts](ui/app/queries.ts) and were validated with `dtctl` against the demo environment. The ActiveGates tab also reads self-monitoring metrics (`timeseries`, at most 10 metric keys per block, so its per-ActiveGate query is three appended blocks) and `dt.system.events`; on the demo tenant its 30-day queries take about a second. The Databases tab's queries take 0.3–0.5 s for 24 hours and 2–4 s for 30 days on the demo tenant: the database processes are found in an `id in [subquery]` prefilter, because `expand` and a lookup in one pipeline over the whole process table took 6–11 s. The Extensions tab's queries take under 0.1 s each for status and fastcheck, and 0.9 / 0.7 / 2.6 s for the recommendations at 24 hours / 7 / 30 days.

## Problem notifications tab: workflow creation setup

Only apps provided by Dynatrace may request `automation:workflows:write` (installing a custom app that asks for it fails with *Only apps that are provided by Dynatrace can use the 'automation:workflows:write' scope*). The app therefore lists workflows with its own `automation:workflows:read`, and creates them through the `workflows` app function ([api/workflows.function.ts](api/workflows.function.ts)) with a platform token:

1. In [My platform tokens](https://myaccount.dynatrace.com/platformTokens) (Account Management), create a platform token for the environment with `automation:workflows:read` and `automation:workflows:write`. The token only works within its user's permissions, and the workflows it creates are owned by that user: generate it for a service user so they keep running when people leave.
2. After **Validate** in **Problem notifications › Remediation actions › Convert classic problem notifications to simple workflows**, paste it into the *Platform token for creating workflows* card. It is stored in the credential vault as the **Token** credential `architect-assistant-workflows` (App Engine scope). *Only I can use it* (default) makes it owner-only; turning it off lets every user of the app create the workflows as the token's user.

The card checks the token by listing workflows with it, and **Create workflows** stays disabled until that works. The function calls the environment's own URL (a relative `/platform/...` call would carry the app's credentials instead of the token); that host needs no entry in the allowed outbound connections. It only creates workflows shaped like the migration's (simple, the migration description, a Davis problem trigger, one Email / Slack / ServiceNow incident / HTTP request task), so a shared token cannot be used to run other workflow code as its user.

## Frontends tab: user tagging setup

User tag rules are only exposed by the classic Config API v1 (`GET /api/config/v1/applications/web/{id}` → `userTags`), which the platform does not proxy. To score user tagging:

1. Create an API token with the **Read configuration** (`ReadConfig`) scope.
2. In the credential vault, add a **Token** credential named `architect-assistant-readconfig` with the **App Engine** scope.
3. Make sure the classic host (`<env>.live.dynatrace.com`) is in `builtin:dt-javascript-runtime.allowed-outbound-connections`.

Or let the app do it: **Frontends › Actions › Set up the user tagging token** creates the ReadConfig token and stores it (or stores one you paste).

Until the credential exists, user tagging shows as *Not measured* and is left out of every average. The function ([api/user-tags.function.ts](api/user-tags.function.ts)) makes one GET per application, 8 in parallel.

## Frontends tab: actions

Every API action is one Settings API POST for any number of frontends, with a Validate (dry run) step and a confirmation checkbox. Checks without an API link to the Dynatrace page instead.

| Action | Kind | Calls | Notes |
| --- | --- | --- | --- |

| Create health alerts | API | 1 POST, one `builtin:health-experience.frontend-alert` object per alert type (max 100 frontends each) | Recommended web types preselected (LCP, INP, CLS, user action duration, request errors, exceptions); frontends that already have an enabled alert of a type are skipped; schema-default analyzers; actor defaults to the current user (a service user is recommended); 300 alerts per environment |
| Assign an existing synthetic monitor | API | 1 GET + 1 POST (`builtin:synthetic.browser\|http.assigned-applications`, scope = monitor) | Current assignments are read and kept; max 100 applications per monitor |
| Create a synthetic monitor | Link | Intent `dynatrace.synthetic/create_synthetic_monitor_with_assigned_frontends` | Opens the Synthetic app with the selected frontends assigned |
| Assign owning team | API | 1 POST `/api/v2/tags` per entity type and 60 entities | Adds `<key>:<team>` (key dt.owner, owner or team; team picked from `builtin:ownership.teams` or typed). The tags API has no dry run, so Validate checks the input and that the team exists. Also on the Ownership tab for frontends and synthetic monitors |
| Set up the user tagging token | API | Auto: 1 POST API token (ReadConfig only, 365 days, owned by you) + 1 vault create/update; Paste: 1 vault create/update | Stored as the Token credential `architect-assistant-readconfig`, APP_ENGINE scope, not owner-only so every app user can score user tagging. If creating API tokens is not allowed for you, paste a token |
| Configure user tagging | Link | Intent `dynatrace.classic.web/view-application` per frontend | Edit > Capturing > User tags, or `dtrum.identifyUser()`; no Settings 2.0 schema, so no bulk API |
| Open frontend settings | Link | Intent `dynatrace.experience.vitals/view-frontend` (Settings tab) per failing frontend | Per-frontend RUM, Session Replay and health alert settings |
